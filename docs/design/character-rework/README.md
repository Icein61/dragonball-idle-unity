# 现有15卡重构设计流程

## 当前填写入口（2026-11-19）

使用 `outputs/character-rework-20261116/角色设计简表-新版.xlsx`。工作簿只有一张「角色设计」页，左边放概念图，右边填写名字、时期、普攻、绝招、必杀和被动。C/B/A/S 与是否上线保留为选填下拉，空白表示待定。可分批交回；每张填完即可进入讨论。原简表、详细表和v5分类表保留为历史资料。

新版使用原项目中用户编辑过的简表为来源。15张既有卡按原稳定CardId和顺序迁入，9张已填写的时期与技能文案逐字核对，9张概念图以标准嵌入图片保留原始内容。新布局坐标见 `form-simple-v3-map.json`。新增角色可复制整块，稳定ID由实现时维护。填写「是」表达投放意图，仍需在游戏中按版本接入。

解包资料用于研究UI层级、技能/装备/道具图标的辨识方式、角色建模比例与绑定思路、动画节奏与关键姿势。后续按用户设计原创制作，或采用用户提供且有权使用的素材。角色身份、时期和技能含义以简表与后续确认为准。

## 历史填写约定（2026-11-16）
当前请使用`outputs/character-rework-20261116/角色设计表-简版.xlsx`，共15张现有卡，每张仅名字、概念图、时期描述、普攻描述、绝招描述、必杀描述、被动描述七项。名字预填可改；概念图可粘贴图片或填链接/文件名。其余内容不要求用户填写，代理依据描述分析补充。旧表保留为历史，不再要求填写旧表的额外字段。

技能相关描述必须逐字保留用户原文，不擅自替换、删减、改写效果或加上新条件。数值、身份/定位、队长、成长及实现建议在代理方案中单独列出；用户写明的技能数值也属于原文，不直接改掉。若补充建议会改变其技能含义，或遇到歧义/与已确认规则冲突，先明确指出并请用户裁定，不能用“润色”覆盖。仅在用户未指定的数值或实现细节上自主补全，记录为代理默认。

简版不预填旧技能，避免混为用户新设计。`form-v2-map.json`记录各区块与稳定CardId、填写单元格的对应关系，由代理维护，用户无需填写工程标识。收到文件后读取文字及概念图，保留原稿并增量处理；不能用生成脚本覆盖用户内容。表格结构检查与首/中/末区块渲染已执行，没有打开Excel窗口。

2026-11-16：用户要求新建角色设计配置表，由用户填写基本设计，代理润色、调整数值并实际落地，从当前15卡开始重构。这是新的开发优先级，不再先扩展角色或剧情。

填写文件：`outputs/character-rework-20261116/角色设计配置表.xlsx`。只编辑“填写设计”的黄色栏，可先提交一张。写清想实现的特色、招式、被动、队长与动作即可，数值允许留空交代理调整。空白代表未提供；明确写“沿用”才将该项旧方案作为新设计。蓝色栏由代理补充，不覆盖用户原话。灰色现状和“当前数值基线”是v0.5.2原型快照，不代表用户已确认新设计。

## 收到填写内容后

1. 按CardId对照用户原稿，保留原话；整理明确机制、触发条件、目标、费用、时长、例外与演出要求。合理细节自主默认，单独标注；不再逐项要求确认。
2. 用既有类别和贡献计时实现设计，补充属性强弱、招式倍率、冷却、怒气、触发条件与强度代价，记录修改原因。队长标签必须来自本人身份，定位词不创造新乘区。
3. 原CardId与人物/阶段不改指向。涉及新阶段/新人物时另建卡；旧成长、装备、预设及存档必须有迁移路径。
4. 将润色方案落实到角色定义、战斗逻辑、UI说明、立绘/小人动作、招式特效、获取及成长配置。表格本身不是运行配置，不会自动热更新；填表或文字润色不算角色已经实现。
5. 针对具体机制和极端组合做核心验证，比较胜率、行动数及团队收益；做Unity后台构建、隔离静音Player与存档迁移验证。没有模拟/真人证据不宣称2～3小时成长目标通过。
6. 在“落地追踪”逐项填写代码/动作/测试证据及版本提交。程序测试与可见观感分别记录；窗口权限仍未恢复。可玩版本按源码与PC包对应规则交付。

初始15卡均为“待填写”，没有冒充用户设计或已完成重构。重复卡分支可以在表中提案，但当前实现尚未完成，必须在追踪中保留真实状态。
